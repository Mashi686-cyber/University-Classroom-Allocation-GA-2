# Genetic Algorithm Design

## 1. Problem Representation
The problem is modeled as assigning every course to exactly one `(Classroom, Time_Slot)` combination, such that hard constraints (capacity, facilities, conflicts) are strictly satisfied, and soft constraints (utilization) are maximized.

## 2. Chromosome Design
The chromosome represents a complete allocation of all courses. It is implemented as a dictionary mapping each `Course_ID` to a specific Gene. This structure is highly efficient for random access during fitness evaluation, crossover, and mutation, ensuring that every course is accounted for exactly once.

## 3. Gene Design
A single gene represents the assignment for a specific course.
- **Value format**: `(Classroom_ID, Time_Slot_Window)`
- **Duration Handling**: The `Time_Slot_Window` is a comma-separated string containing consecutive timeslots (e.g., `"TS001,TS002"`). This ensures that courses with `Duration > 1` are inherently assigned to contiguous time blocks, preventing fragmentation.
- **Valid Domains**: Genes are only populated from pre-calculated valid timeslot windows and existing classroom IDs, ensuring baseline structural validity before constraint checking.

## 4. Initial Population
The initial population is generated by randomly selecting feasible `(Classroom, Time_Slot_Window)` pairs for each course. Because this random generation is blind to other courses' assignments, the initial population will naturally contain many conflicts (e.g., overlapping lecturers or student groups). A fixed random seed (`42` by default) ensures absolute reproducibility.

## 5. Fitness Function & Penalty Strategy
The fitness function is penalty-based. Hard constraints incur massive negative penalties to drive the population toward feasibility, while the soft objective (utilization) provides small positive rewards to differentiate between equally feasible solutions.

- Unallocated courses: `-100,000` (Worst offense)
- Classroom, Lecturer, Student Group conflicts: `-10,000` per conflict
- Capacity, Facility, Room Type violations: `-10,000`
- Utilization score: `+0 to +100`

*Double Counting Handling*: A conflict is counted as `N - 1` violations. If 3 courses overlap for a single lecturer, it counts as `3 - 1 = 2` conflicts. This is identical to the baseline constraint checker.

## 6. Selection
**Tournament Selection (k=3)** is used. It selects 3 individuals randomly and picks the one with the highest fitness. This maintains a healthy balance of selection pressure and diversity.

## 7. Crossover
**Uniform Crossover** is employed. For each course, the child randomly inherits the gene from Parent 1 or Parent 2 (50% probability). Unlike 1-point crossover, uniform crossover is ideal here because courses are discrete, non-sequential entities; their order in an array carries no spatial meaning.

## 8. Mutation
Random **Resetting Mutation**. With probability `mutation_rate`, a gene is entirely replaced with a new random, valid `(Classroom, Time_Slot_Window)` pair. No complex algorithmic repair is used; the GA relies purely on the evolutionary pressure of the penalty function to find valid configurations.

## 9. Elitism
The top `N` individuals (default 2) are copied directly to the next generation without modification. This ensures that the best-found solution is preserved and not accidentally destroyed by crossover or mutation.

## 10. Termination Criteria
The algorithm terminates when either:
1. A predefined maximum number of generations is reached.
2. An optimal feasible solution is found (fitness > 0, meaning absolutely zero hard constraint penalties).

## 11. Initial Parameter Configuration (Development)
- **Population Size**: 50
- **Generations**: 100
- **Crossover Rate**: 0.8
- **Mutation Rate**: 0.1
- **Elitism**: 2
- **Seed**: 42

## 12. Computational Complexity
Evaluating a single chromosome takes `O(C)` where `C` is the number of courses (using hash map lookups for constraint checks). The total complexity per generation is `O(P * C)` where `P` is population size. Overall complexity: `O(G * P * C)` where `G` is generations.

## 13. Assumptions & Limitations
- **Assumption**: Penalty weights are appropriately scaled.
- **Limitation**: The purely random initial population might struggle to find a feasible solution in highly constrained large datasets without advanced initialization heuristics.

## 14. Hard Constraint Priority and Feasibility
- **Why hard constraints need stronger penalties**: If hard constraints were weighted lower than the penalty for an unallocated course, the GA could actively choose to create broken schedules (e.g., massive capacity violations) simply to avoid leaving a course unallocated. By making all hard constraints massive (10,000) and unallocated extreme (100,000), we guarantee that any violation mathematically eclipses the maximum possible utilization score (100). This ensures the GA optimizes for feasibility first, and utilization second.
- **Why utilization is secondary**: Utilization is only meaningful for a physically possible and conflict-free schedule.
- **Feasibility Evaluation**: The generated datasets contain random relationships. A feasibility check script on the SMALL dataset revealed that 3 courses were given requirements (e.g., a "Laboratory" room type combined with 120 students) that physically do not exist in the generated classroom pool. Therefore, absolute feasibility is mathematically impossible for these courses, and they are intentionally left unallocated.
- **Repair Mechanism**: We implement a lightweight deterministic repair strategy during Initialization and Mutation. Instead of randomly picking *any* classroom, the operator filters the classroom pool to only include rooms that satisfy Capacity, Room Type, and Facilities. If no such room exists, the course is marked as Unallocated rather than forcing a broken assignment.
